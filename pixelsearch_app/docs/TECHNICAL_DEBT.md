# TECHNICAL DEBT

Tracked, intentional shortcuts. Each has a trigger for when it must be paid down.

| # | Debt | Why it's OK for now | Pay down when |
|---|------|---------------------|---------------|
| TD-1 | Keyword search remains as an intentional fallback (`search_engine.dart`) — **RESOLVED as a primary path 2026-08-08** | `SemanticSearchBackend` now performs CLIP text embedding and cosine retrieval; keyword-only search is used only on web or when the model is unavailable | retain as graceful degradation unless every target guarantees model provisioning |
| TD-2 | Embeddings stored as **float32** blobs (~2 KB/photo) | simple, lossless, fast to load | if DB size hurts at 50k → fp16 blobs (halves it) |
| TD-3 | Brute-force cosine scan is the active `VectorIndex`; no ANN index | exact and simple for the intended library sizes, but linear in the number of indexed photos | if measured query latency exceeds budget → sqlite-vec / ObjectBox HNSW |
| TD-4 | **Web has no DB backend** (native-only drift connection) | Android-first; web is a verification/demo target | if web becomes a real target → drift-wasm worker |
| TD-5 | Sample photos are **hardcoded** in `sample_data.dart` — **RESOLVED 2026-08-08** | deterministic demo | done: device indexing is now the only library source; `samplePhotos` and the M1 demo loader were deleted (ADR-015) |
| TD-6 | Cached thumbnail files have no eviction, validation, or regeneration policy | `FileThumbnailGenerator` writes compact files outside SQLite, avoiding full-image decode on grid display | if cache eviction or stale paths become visible → add bounded cache management and async regeneration |
| TD-7 | Manual DI via Riverpod (no formal DI container) | idiomatic, testable, light | only if wiring complexity grows materially |
| TD-8 | preprocessing constants hand-declared, unverified — **RESOLVED 2026-08-06** | verified vs open_clip in the M4 preflight (contract v1.1) | done |
| TD-9 | image preprocessing extracts pixels via `image.getPixel` (per-pixel object alloc) — **RESOLVED 2026-08-08** | was fine for the gate (6 imgs); on-device indexing measured it at ~445 ms/photo | done: reads the packed RGB buffer via `getBytes`. Values are the same uint8 samples widened to double — the preprocessing fingerprint is unchanged (`sum=100051.464714`), so embeddings are bit-identical |
| TD-10 | CLIP tokenizer `basic_clean` approximates ftfy as identity + minimal HTML unescape | verified exact on 19 cases incl. accented Unicode; real queries don't need ftfy | add an ftfy-equivalent only if a real query ever mismatches |
| TD-11 | M5 device adapters written + compile-verified but **not runtime-tested** (needs Android + plugin native side) | core is fully tested; adapters are thin port impls that compile clean | run on a device: WorkManager reboot/backoff, ML Kit inference, MediaStore scale, latency/memory |
| TD-12 | M6 `searchBackendProvider` rebuilds when `indexWarmupProvider` lands (loading→data), rebuilding the `SemanticSearchBackend` (embedder + tokenizer re-created via the conditional-import factory) | at most one transition; the ORT session is lazy, so no model reload unless a search was already in flight, and the old session is reclaimed at process exit | if it ever matters: cache the tokenizer + expose `SearchBackend.dispose()` to release the prior embedder |
| TD-13 | M6 in-memory `VectorIndex` isn't updated *during* an indexing run — only rebuilt when it ends (KI-6) | `IndexingController` invalidates `indexWarmupProvider` on completion, so a session that indexes can then search; only searches issued mid-run miss the in-flight batches | subscribe the index to the indexer's progress/commit stream and `upsert` deltas instead of a full reload |
| TD-14 | M6 `semanticMinCosine` (0.15) + hybrid weights (0.70/0.25/0.05) are measured/heuristic defaults, not tuned on a labeled set (KI-5) | measured on the 6-image parity set; ranking (argmax) is unaffected | M14: precision/recall + weight ablation on a labeled photo corpus |
| TD-15 | The whole library is loaded into memory (`PhotoRepository.loadPhotos()` → `List<Photo>`) and re-loaded wholesale after each indexing run | rows are metadata only (no pixels); fine at the scales measured so far | at 50k, or if refresh latency shows: page the grid off the DB (`LIMIT/OFFSET` or a drift stream) rather than holding the full list |
| TD-16 | `Photo.image` returns a `FileImage` without checking the thumbnail file exists | an `existsSync` per tile per frame is sync I/O on the UI thread — strictly worse; a stale path degrades to Flutter's image error path | if evicted thumbnails become common, have the indexer re-generate on read, or verify asynchronously in the tile |
| TD-17 | Indexing runs entirely on **one isolate**; measured at ~0.9 of a single core with 7 of 8 idle | `IndexingService` now yields between assets so the UI can paint and cancel between photos, but decode/preprocess/ONNX remain synchronous within an asset | Tier 2 perf: bounded worker-isolate pool for decode/preprocess/ML Kit, inference on 1–2 isolates (each fp32 ORT session costs ~86 MB) |
| TD-18 | Full-resolution pure-Dart JPEG decode is now the single largest stage (~28%, 546 ms at 12 MP; scales with resolution) | it is the only path that preserves the frozen preprocessing contract exactly | Tier 3 perf: decode a native downscaled thumbnail instead. **Changes the pixels CLIP sees** ⇒ `embedding_version` bump + full re-index (MIGRATIONS.md §B) and explicit approval |
| TD-19 | `PhotoManagerGallerySource.listAssets()` materializes every `AssetRef` before reconciliation | pixels are still processed one at a time and batch results remain bounded, but gallery metadata memory grows with library size | measure a 10k+ library on device; if material, extend the gallery/reconciliation contract for pagewise scanning without weakening incremental correctness |

None of these block current work. TD-8/KI-1 (preprocessing verification) was resolved in the M4 preflight.
